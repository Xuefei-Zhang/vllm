📋 问题 & 结论

现象：本地 vLLM 部署 Qwen3.6-27B 后，模型在长文本生成（尤其是代码场景）中进入病态重复循环——输出反复重复同一个短语，不会自行停止。 Broken

根因：Thinking mode 默认开启，模型在输出最终答案前产生长篇推理内容。当推理过程遇到代码中的重复性模式（如 Python list comprehension [x for x in ...]）时，模型陷入推理循环，不断重复生成相同短语直到填满 token 预算。

修复：Fixed 去掉不兼容的 speculative decoding（MTP 方法不匹配），关闭 thinking mode 后模型输出稳定。另外两个参数也错误：--tool-call-parser hermes（应为 qwen3_coder），缺少 --reasoning-parser qwen3。

🔍 根因分析

1. Qwen3.6 默认 Thinking Mode

Qwen3.6 是一款 thinking 模型——它在给出最终答案前，会先生成 <think>...</think> 推理过程。 这个推理过程在遇到结构化/重复性内容（如 list comprehension、嵌套循环）时，会进入自激循环： 模型在推理中不断 restate 同一个模式，无法自己跳出。 

# 正常推理（非代码 prompt）
"Explain general relativity" → 思考 → 回答 ✅

# 故障推理（代码 prompt）
"写一个快速排序" → 思考 → 撞到 [x for x in → 死循环 ❌

# 关掉 thinking 后（代码 prompt）
"写一个快速排序" + enable_thinking=false → 直接回答 ✅

2. Speculative Decoding 方法不匹配

vLLM 支持多种 MTP (Multi-Token Prediction) 方法。用户用了通用 method: mtp，但 Qwen3.6 需要架构特定的 method: qwen3_5_mtp。 代码中 qwen3_5_mtp 会从 config 读取 mtp_num_hidden_layers 并正确配置 Qwen3_5MTP 架构。 通用 mtp 方法跳过此配置，导致 draft token 质量差 → 加剧了重复问题。

Note 即使改为正确的 qwen3_5_mtp，thinking mode 下的代码重复问题仍存在。最终选择完全移除 speculative decoding 以换取稳定性。

3. Tool Call Parser 错误

Qwen3.6 使用 qwen3_coder 格式输出工具调用（tool call），但用户配置了 hermes parser。 两种格式不兼容，当 OpenCode 等客户端请求工具调用时，vLLM 可能错误解析模型输出，产生乱码或空内容。

4. 缺少 Reasoning Parser

没有 --reasoning-parser qwen3 时，模型的 <think>...</think> 原始文本直接暴露在 content 字段中。 客户端（OpenCode）收到的是混杂了推理标记的原始输出，无法正确提取最终答案。

Python SDK 调用示例

from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8000/v1",
    api_key="EMPTY",
)

# 推荐：关闭 thinking 模式（稳定）
response = client.chat.completions.create(
    model="qwen3.5-27b",
    messages=[{"role": "user", "content": "写一个快速排序"}],
    max_tokens=8192,
    temperature=0.7,
    extra_body={
        "chat_template_kwargs": {"enable_thinking": false}
    },
)

# 如需 thinking 能力（推理+答案）
response = client.chat.completions.create(
    model="qwen3.5-27b",
    messages=[{"role": "user", "content": "证明哥德巴赫猜想"}],
    max_tokens=16384,     # 必须足够大，thinking 消耗大量 token
    temperature=1.0,
    top_p=0.95,
    extra_body={"top_k": 20},  # 不传 enable_thinking=false → 默认 thinking
)

# 有工具调用时（OpenCode 场景）
response = client.chat.completions.create(
    model="qwen3.5-27b",
    messages=[{"role": "user", "content": "北京的天气怎么样？"}],
    tools=[{
        "type": "function",
        "function": {
            "name": "get_weather",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {"type": "string"}
                },
                "required": ["location"]
            }
        }
    }],
    tool_choice="auto",
)

💡 经验总结

  1. Thinking 模型 ≠ 普通指令模型 — Qwen3.6 默认 thinking 模式，推理内容会 restate prompt，容易误判为"重复"。客户端必须能处理 reasoning / content 分字段输出的格式。
  2. 看官方文档，不要只看社区配置 — vLLM 的 --tool-call-parser、--reasoning-parser、--speculative-config 都是模型架构特定的。Qwen3.6 的 HuggingFace README 明确写着这些参数。
  3. Speculative Decoding 是双刃剑 — MTP 能提速但稳定性可能下降。对于生产环境，优先确保正确性再考虑优化。
  4. 长文本测试不可跳过 — 很多问题只在 >512 tokens 的长生成中暴露（如重复循环）。短文本测试全部通过 ≠ 系统可用。
  5. vLLM 源码注释了参数 — vllm/config/speculative.py 第 512 行明确写着 if self.method in get_args(MTPModelTypes) and self.method != "mtp":，通用 mtp 方法被排除在自动检测之外。

🚀 一键重启

#!/usr/bin/env bash

# 停旧进程
pkill -f "vllm serve"
sleep 3

# 启动（无 speculative decoding，128K context）
nohup /home/xuefeiz2/3rd/vllm/.venv/bin/python3 \
    /home/xuefeiz2/3rd/vllm/.venv/bin/vllm serve \
    /home/xuefeiz2/models/Qwen3.6-27B \
    --served-model-name qwen3.5-27b \
    --dtype bfloat16 \
    --kv-cache-dtype fp8 \
    --max-model-len 131072 \
    --gpu-memory-utilization 0.90 \
    --max-num-seqs 16 \
    --enable-chunked-prefill \
    --enable-prefix-caching \
    --trust-remote-code \
    --reasoning-parser qwen3 \
    --enable-auto-tool-choice \
    --tool-call-parser qwen3_coder \
    --host 0.0.0.0 --port 8000 \
    > ~/vllm.log 2>&1 &

echo "PID: $!"

# 等待就绪
until curl -s http://localhost:8000/health > /dev/null; do
    sleep 5
done
echo "Server ready"
